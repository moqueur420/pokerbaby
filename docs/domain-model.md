# Контракты базовых типов: этап 2

Публичный API находится в `io.pokerbaby.engine`. Зависимостей времени выполнения у ядра нет. Оценщик добавлен на этапе 3 и описан в [отдельном документе](hand-evaluator.md). Движок торговли, воспроизведение и JSON ещё не реализованы.

## Карты и колода

Карта записывается ровно двумя символами: достоинство `23456789TJQKA` и масть `cdhs`. Регистр значим; пробелы не удаляются. Примеры: `As`, `Td`, `2c`. Достоинства имеют значения 2—14; особый случай туза в младшем стрите будет обрабатывать оценщик.

Каноническая колода: сначала все трефы от двойки до туза, затем бубны, червы и пики в том же порядке. `Deck.standard()` возвращает 52 карты без перемешивания.

Перемешивание зафиксировано:

1. Исходный порядок — каноническая колода.
2. Алгоритм — обратный Fisher–Yates: индексы от последнего до 1 меняются местами со случайным индексом от 0 до текущего включительно. Сортировка по случайным ключам и обмен со случайной позицией всей колоды не используются (К-6).
3. `Deck.shuffled(long)` использует `java.util.Random` с явно переданным seed. `Deck.shuffled(RandomGenerator)` читает равномерные исходные значения через `nextInt()` и не сохраняет генератор внутри колоды.
4. Движок сам выбирает индекс без смещения (К-7). Из исходного `int` берутся 31 равномерный бит: `nextInt() >>> 1`, диапазон значений — `[0, 2^31)`. Для размера интервала `bound` принимается только диапазон `[0, limit)`, где `limit = 2^31 - (2^31 % bound)`. Значения от `limit` отбрасываются, после чего запрашивается новое число. Остаток от деления вычисляется только для принятого числа.
5. Если `bound` — степень двойки, весь диапазон делится без остатка. Используются равные по размеру группы старших битов, без отбраковки. Такое отображение сохраняет прежние результаты `java.util.Random.nextInt(bound)`; алгоритм этого генератора описан в [документации Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/Random.html#nextInt(int)).

Порядок всех 52 карт для seed 42 закреплён тестом совместимости. Для другого типа генератора результат определяется его алгоритмом и текущим состоянием.

`Deck.shuffled(List<Card>, long)` и `Deck.shuffled(List<Card>, RandomGenerator)` применяют тот же алгоритм к заданной полной или частичной колоде. Входной порядок и список не изменяются, новая колода имеет позицию 0.

`ShuffleTest` перебирает все 24 допустимых сочетания индексов для четырёх карт и отдельно принудительно проверяет отбраковку. Статистическая проверка использует один `Random(42)` на 2 400 000 тасовок исходных четырёх карт; повторное создание генератора внутри цикла недопустимо, поскольку оно повторяло бы одну перестановку. Все 24 частоты должны входить в диапазон 99 000—101 000. Тест входит в обычные `test`, `check` и `build`. При фиксированном генераторе и seed результат воспроизводим; частотная проверка дополняет проверки алгоритма и отбраковки.

Колода хранит неизменяемый исходный список и позицию чтения. `cards()` включает сданные карты, `remainingCards()` — только ещё не сданные. `draw()` возвращает `Deck.Draw(card, deck)`; исходный объект не меняется. Повторное обращение к прежнему объекту позволяет воспроизвести или разветвить тот же розыгрыш.

`Deck.ordered` принимает также пустую и частичную колоду; повторы и null запрещены. Потребитель проверяет запас карт через `requireRemaining`: начало раздачи потребует 9, возобновление — число недосданных общих карт. Связь остатка колоды с известными картами раздачи будет проверять `resume` на своём этапе.

## Фишки и конфигурация

`SeatChips` хранит ровно два неотрицательных `long` в неизменяемом списке. Сумма не превышает 2·10¹². Значения и сумма проверяются при создании; сумма считается через `Math.addExact`. `with(seat, amount)` возвращает новый объект.

Контекстные проверки:

| Метод | Допустимые значения |
| --- | --- |
| `validateMatchStart()` | Каждый стек от 1 до 10¹² |
| `validateHandStart()` | Оба стека положительные; общий предел 2·10¹² сохраняется |
| `validateResume(contributions)` | Нулевые стеки допустимы; стеки и вклады вместе не превышают 2·10¹² |

Такие проверки будут вызываться соответствующими операциями матча и движка. Сам тип допускает ноль, поскольку используется также для вкладов и текущих стеков. Сохранение исходной суммы фишек будет проверять игровой движок.

`GameConfig` требует `1 <= smallBlind <= bigBlind <= 10¹²`. По умолчанию блайнды 50/100, стартовый стек — 10 000 на игрока.

## Метаданные и действия

`HandMeta` принимает идентификатор раздачи, список двух различных идентификаторов игроков и `Optional<Instant>` с временем начала. Идентификаторы не могут быть пустыми или состоять из пробелов. Время и идентификаторы не генерируются внутри библиотеки.

`Action` содержит тип и `OptionalLong to`. Для BET и RAISE сумма обязательна и положительна; для FOLD, CHECK и CALL она отсутствует. Сумма означает полный вклад на текущей улице после действия. Верхний предел ставки и её доступность определяются состоянием раздачи и будут проверяться в `legalActions`/`apply`.

Для игровых ошибок подготовлен `IllegalActionException` с кодами `NOT_YOUR_TURN`, `HAND_COMPLETE`, `ACTION_UNAVAILABLE`, `BELOW_MINIMUM`, `ABOVE_MAXIMUM`. Пока это контракт исключения; отклонение действий движком появится вместе с торговлей.

## События и заголовок истории

`HandHistory.Header` объединяет версию схемы 1, `GameConfig`, `HandMeta`, стартовые стеки раздачи и место баттона. JSON-модуль позднее преобразует эти значения в поля формата ТЗ.

Семь типов `HandEvent` соответствуют схеме: `PostBlind`, `DealHole`, `ActionTaken`, `DealBoard`, `ReturnUncalled`, `Showdown`, `Payout`. Метод `type()` возвращает имя события из ТЗ. Денежные события содержат только положительные суммы; списки карт проверяются на размер, null и внутренние повторы. `DealBoard` содержит только новые карты улицы; `Showdown` — две закрытые карты игрока и объявленную категорию.

Конструкторы проверяют форму данных. Неполная история допустима; очерёдность ходов, повтор карты между разными событиями и правильность выплат проверит воспроизведение. В частности, повторное указание тех же карт в `deal_hole` и `showdown` само по себе корректно.

`append` сохраняет точный порядок событий и возвращает новую историю. Для генерации историй движком фиксируем порядок:

1. Блайнд баттона, затем блайнд второго игрока.
2. По одному агрегированному `deal_hole` для мест 0 и 1; внутри каждой пары сохраняется порядок получения карт. Фактическая сдача идёт по одной карте по очереди, начиная с игрока без баттона.
3. Действие игрока, затем вызванные им автоматические события.
4. При закрытии торговли положительный возврат неуравненной суммы предшествует досдаче борда и выплате.
5. Общие карты идут по улицам; события вскрытия и выплаты упорядочиваются по месту игрока. После фолда вскрытия нет. Нулевые возвраты и выплаты не создаются.

Этот порядок будет реализован при добавлении игрового движка; текущие типы событий не запускают переходы сами.
