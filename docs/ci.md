# Быстрые и тяжёлые проверки

Задача 7 ТЗ на оптимизацию. Рабочая ветка: `ci/split-fast-slow-tests`.
Основание ветки: `b6179d2d87cefdbe50ad63e2d85c5d61da1db544`.

## Локальный запуск

```powershell
# Быстрые тесты всех модулей, Javadoc, JaCoCo и дистрибутивы
.\gradlew.bat build

# Только быстрые проверки без сборки дистрибутивов
.\gradlew.bat check

# Только тяжёлые тесты
.\gradlew.bat slowTest

# Полный набор
.\gradlew.bat build slowTest

# Одна тяжёлая проверка
.\gradlew.bat :poker-engine-core:slowTest --tests io.pokerbaby.engine.EngineFuzzTest.largeCorpus
```

Обычный `test` исключает тег `slow`. Задача `slowTest` использует те же тестовые
классы и ресурсы, но включает только этот тег. Параметр `--tests` дополнительно
ограничивает выбранный набор, не отменяя фильтр тегов. В модулях без тяжёлых
тестов пустой `slowTest` завершается успешно.

`check` и `build` не зависят от `slowTest`. Отчёт JaCoCo и проверка порога 90 %
используют только обычный `test`. У `slowTest` отдельный файл данных JaCoCo,
который не включается в отчёт быстрых тестов.

В быстрых тестах 270 выполнений, включая 255 в ядре и 15 в веб-модуле.
В тяжёлом наборе ровно семь тестов ядра. Исходные объёмы, seed, утверждения и
ожидаемые значения тяжёлых проверок сохранены. Общая логика уменьшенных и полных
версий вынесена в тестовые вспомогательные методы. `SeededHands` и golden-файл
не изменялись.

## GitHub Actions

| Событие | Job `build` | Job `slow` |
| --- | --- | --- |
| Push в рабочую ветку | Ubuntu + Windows | — |
| Pull Request | Ubuntu + Windows | — |
| Push в `main`, включая слияние PR | Ubuntu + Windows | Ubuntu |
| Ежедневное расписание | — | Ubuntu |
| Ручной `workflow_dispatch` | Ubuntu + Windows | Ubuntu |

Расписание: `17 3 * * *`, 03:17 UTC / 06:17 по Москве. GitHub запускает
плановый workflow из основной ветки. Ручной запуск также позволяет проверить
тяжёлые тесты в выбранной рабочей ветке до слияния.

Бенчмарков в workflow нет: производительность измеряется локально.
Артефакты быстрых проверок называются `fast-reports-ubuntu-latest` и
`fast-reports-windows-latest`; тяжёлых — `slow-reports-ubuntu`.
HTML-отчёты локально находятся в `build/reports/tests/test/` и
`build/reports/tests/slowTest/` соответствующего модуля.

## Проверка перед PR

- `build` прошёл; покрытие строк ядра по быстрым тестам — 1 041 из 1 042, 99,90 %.
- `slowTest` прошёл и выполнил в точности все семь помеченных тестов.
- SHA-256 файла данных и XML-отчёта покрытия быстрых тестов не изменился после
  запуска `slowTest`.
- YAML workflow, условия для push/PR/расписания/ручного запуска, матрица ОС и
  команды jobs проверены локально.
- Ограничение `JvmVendorSpec.ADOPTIUM` удалено; требование Java 21 и Foojay
  сохранены.
- Полная сборка с повторной компиляцией, Javadoc и 270 быстрыми тестами прошла
  на Microsoft OpenJDK `21.0.13.0.2+1-LTS` при отключённых автообнаружении и
  скачивании других JDK. Сборочный кеш также был отключён. ZIP для этой проверки
  взят с [официальной страницы Microsoft](https://learn.microsoft.com/en-us/java/openjdk/download)
  и проверен по опубликованной SHA-256; системная установка Java не менялась.

В одном локальном прогоне на той же машине и Temurin 21 суммарное время тестовых классов ядра уменьшилось
с 12,503 до 4,651 секунды, в 2,69 раза. Это время выполнения тестов из XML
JUnit; оно не включает конфигурацию Gradle, компиляцию, Javadoc и подготовку CI.

Чтобы проверить установленный JDK другого поставщика без автоматической замены,
можно явно указать единственный путь (замените пример на свой):

```powershell
$taskJdk21 = 'C:\path\to\installed-jdk-21'
& "$taskJdk21\bin\java.exe" -jar gradle/wrapper/gradle-wrapper.jar build --no-daemon --offline --no-build-cache --rerun-tasks "-Dorg.gradle.java.installations.paths=$taskJdk21" -Dorg.gradle.java.installations.auto-detect=false -Dorg.gradle.java.installations.auto-download=false
```

Исходное время CI взято из [сборки main до изменений](https://github.com/moqueur420/pokerbaby/actions/runs/43542001513):

| Job | До: весь job | До: шаг Gradle | После |
| --- | ---: | ---: | --- |
| Ubuntu | 25 с | 14 с | Проверить после отправки PR |
| Windows | 44 с | 21 с | Проверить после отправки PR |

После публикации требуется записать время новых jobs и проверить критерий
сокращения времени `build` не менее чем вдвое. После слияния в `main` также
проверяется успешный запуск нового job `slow`. До этого эти два критерия
удалённой приёмки остаются открытыми.
